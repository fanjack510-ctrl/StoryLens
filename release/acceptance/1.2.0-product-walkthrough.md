## 为什么需要这份东西

`release/acceptance/1.0.4.md` 与 `1.0.5.md` 记的是**发布工程门禁**——自动化测试、Windows 构建、冒烟、数据升级。那两份文档自己写明：

> `verified` / `ready` … 指的是**发布工程门禁**。它们**不声称每一条变更被最终用户逐项人工验收过**。

于是就有了今天这个局面：

| base_version | 变更数 | 未发布 |
|---|---:|---:|
| 1.0.4 | 17 | **0** ← 最后一次真正发出去的 |
| 1.0.5 | 67 | 66 |
| 1.1.0 | 4 | 3 |
| 1.1.1 | 34 | 34 |
| 1.1.2 | 11 | 11 |
| 1.2.0 | 86 | 86 |
| **合计** | **240** | **202** |

1.1.2 那趟车停在 `rc5-built-awaiting-installed-acceptance`。

**每一条变更都单独测过，但没有任何一刻有人把它们装成一个整体、指着说「这就是它」。** 「项目到底能做啥」说不清，不是因为功能多，是因为没有一个「当前版本」存在过。

这份清单就是那个答案的载体：**打勾的那些，就是 1.2.0 能做的事。**

**D1 的实测与根因（本轮最重要的一条）：** 「分析本章」的弹窗完整——分析范围、执行方式、三档分析模式、正文发送确认，未刷新服务状态前「开始」正确置灰。但刷新之后仍然是「连接状态：配置尚未完成，暂时无法开始」。抓到 preflight 的原始响应：

```
error_code:         PROVIDER_HEALTH_STALE
health_source:      cached_success
health_checked_at:  2026-08-18T16:57:51Z   ← 两天前
health_ttl_seconds: 86400                   ← 24 小时
```

而此时 provider 是 `credential_state: configured` / `connection_state: connected` / `enabled: true`，设置里点「测试连接」明确回「✓ DeepSeek API 连接正常」，短篇分析几分钟前刚用同一个 provider 跑完两轮。

代码里本来有 `apply_validation_snapshot_health`，设计意图正是让设置里的验证覆盖过期的健康状态。**但验证快照是空的**——「测试连接」成功后不写快照，「保存配置」也不写（保存后错误码从 `PROVIDER_HEALTH_STALE` 变成 `PROVIDER_STATE_CHANGED`，仍然 409）。

**结论：健康缓存 24 小时过期后，「分析本章」永久卡死，而 UI 上没有任何一条路径能解除它。** 这道门只存在于 `analysis.py`（单章路径）；全书分析与短篇精读都不经过它，所以它恰好只杀掉工具条上的那个主按钮。阿里云那个表单**根本没有测试按钮**，所以对该 provider 而言原则上就无解。

**修复（09b42911）：** 「测试连接」改为先跑传输诊断、再发一次真实的 32-token 调用，并改名「验证连接」——因为它现在做的就是验证。实测：点击后写入 `validation_status=success` 与当前时刻的 `validated_at`，此前一直拒绝的 preflight 随即变为「配置完成，可以开始」。

**第二处独立故障（同一提交修复）：** `_get_or_create_partition_session` 写的是 `status="partition_ready"`，而响应模型的 `ReviewStatus` Literal 里没有这个值 → 每次读取 partition-ready 的审阅都 pydantic 校验失败返回 500 → 工作台渲染成「当前章节没有待确认的场景划分」。**一个词没写进枚举，就让所有走到该状态的章节都没法确认场景**——书 14 第 4090 章从 08-16 就卡在那里。

**两处修好后，单章分析完整跑通：** 开始 → 边界审阅（给出 5 个场景并确认）→ succeeded，产出 5 个场景与 5 条 `scene_analysis`。

**同时确认：** 新建的 run 28 依然是 `book_id` / `analysis_type` / `scope_type` / `start_chapter_id` **全为 NULL**——这是**当前行为，不是历史遗留**。

**B3 的实测：** 字号 17px → 点两次「增大字号」变 18px → 刷新回到 17px。`uiStore` 是普通 zustand store，`fontSize: 17` 写死默认值，**没有 persist 中间件**，localStorage 里也没有对应键——阅读设置只活在内存里，每次刷新和每次重启应用都回到默认。

**E2 的实测与根因：** 书 12《穿越之种田难为》39 万字**只切出 2 章**，单章 19.4 万字。`plan_windows` 抛 `ValueError: single chapter exceeds safe context capacity: 194412>106000`，一路冒成 500，前端把它归类成连接失败。**这是分章失败与错误分类两个问题叠在一起：真正的原因是「这本书的章切错了」，用户看到的是「服务连不上」。**

**D2 的根因（第四轮查明）：** 内容体的渲染条件是 `activeTab === "scene" && analysisRunId`，而 `analysisRunId` **只从 URL 的 `analysisRun` 参数取**，代码里有一句明确的注释「Do not auto-write analysisRun into the URL」。

所以 `?chapter=4175&view=result` 渲染出的只有外壳（30 个字符）；补上 `&analysisRun=28` 之后**同一页面立刻完整渲染**——侧栏 5 个场景 S01–S05 带边界标记，正文带段落 ID，共 3,427 字符。

不自动绑定运行这个设计意图是合理的（打开书或切章不该把人丢进一份旧分析）。缺陷在于：**明确请求 `view=result` 却没有绑定运行时，页面既不回退到本章最近一次成功的运行，也不说明为什么是空的。**

**我先前把 D2 归因于「运行记录 book_id 为 NULL」，那是错的**——审阅会话里 `book_id` / `chapter_id` / `analysis_run_id` 都写得好好的。当时我标注了「因果未证实」，现在正式更正。

## 十、第六轮：用户实操暴露的三处缺陷（2026-08-20）

### D5：界面要你确认一件已经做完的事，而且没有按钮（已修，64c3f8d0）

《长安的荔枝》第一章：运行 `succeeded`、审阅 `confirmed`、接受 13 条边界、14 个场景、14 条分析产物——**全做完了**。而面板一直显示「待确认场景划分」。刷新无效，因为不是客户端缓存旧了，是**接口本身自相矛盾**：

```
GET /analysis-runs/2
  status           = succeeded
  effective_status = awaiting_scene_boundary_confirmation
```

`effective_chapter_status` 会读一个写在运行上的标记。运行**走到**确认这一步时写下它；而确认动作只往同一份数据里写了自己的字段，**从不更新这个标记**——于是它在这次运行的余生里一直说「还在等」，并且这个判断排在所有实际证据之前。

同一个文件里早就有过一次同样的教训：CHG-013 的注释写着「正在跑的阅读旅程必须压过这个过期的等待标记」。**这次把同一条规则用在了更要紧的一种：已确认的审阅是比没人更新的标记更硬的证据。** 标记本身不动——它记录历史。

**没有按钮，恰恰是因为真的没东西可确认。** 界面在指使人去做一件不存在的事。

## 十一、第七轮：拆文分析跑完了，但报告里看不到（2026-08-20）

### E8：九段拆文内容全在库里，界面上一个字都没有

《我喜欢你的信息素》跑的是**拆文**，不是评测。接口返回的文档里 `story_breakdown` 九个字段全是满的：

```

standout_moments     10

supporting_cast      11
moment_count_rationale / cast_note   有
```

而你在屏幕上看到的是**「全书总览」和「综合诊断」两张空白页**。

原因是两层，缺一不可：

1. **前端根本没有「拆文」这个模块。** `ModuleKey` 里没有它，导航里没有它，渲染分支里没有它——后端算出来的九段内容，前端没有任何位置可以放。
2. **导航是写死的七项。** 总览和综合诊断是**评测**的产物，拆文文档里这两块本来就是空的。页面照样把它们画出来，于是拆文读者看到的就是两页空白，而唯一有内容的部分没有入口。

只补 1 会留着两页空白；只做 2 会让拆文无处可去。**空白页正是这一整天在修的那类问题**，所以两件一起做。

- `WholeBookV2ReportView.tsx` 增加 `StoryBreakdownModule`（起承转合 / 打动人的瞬间 / 每章留下的问题 / 可复用的手法 / 配角功能五个页签），导航改为读过滤后的列表，并在当前模块不在列表里时跳到第一个可用模块。

**这条规则原先只写在 PDF 那一侧。** `printExport.ts` 里早有一个 `PLACEHOLDER` 正则和一条用例
（注释里记着「二十二个人物有十二个」），屏幕和 HTML 导出各自没有。现在三处共用 `saidNothing()`
一份定义，PDF 那侧改为调用它，规则不会再各走各的。HTML 导出另有一处：结果来源那格在
`result_origin` 缺失时会直接印 `unknown`，改成缺失就不印那一段。

### B3：阅读设置改得动，刷新就回去

字号 / 行距 / 正文宽度 / 显示段落 ID 四项只活在 zustand store 里，localStorage 没有对应键。
主题和界面缩放各自有 `lib/` 下的持久化助手，这四项没有——所以嫌默认字号小的人每次开应用
都要再调一次，看起来像这个设置不生效，而不是不保存。

按主题和缩放同样的形状加了 `lib/readingSettings.ts`（读一次、每次改动写一次），没有给整个
store 套 persist 中间件——那会给主题和缩放已经在写的键再加一个写入方。存进去的值在读取时
夹回控件能表达的范围，写失败不抛错：存储满了不该让刚拖动的滑块失灵。

实测：字号调到 18px、行距紧凑、正文宽度窄、打开段落 ID，整页重新加载后四项都在。

### 分析本章对话框里那句过期的话

对话框顶部有一个「分析范围」下拉框，唯一可选项是「当前章节」，另一项写着「全书（后续开放）」，
下面一句提示说**「全书分析将在后续版本开放」**。全书分析早就开放了，就在同一本书的书籍页上。

一个只有一个选项的下拉框不是选择，一句过期的提示比没有提示更糟——它让人以为那条路还不存在。
换成一句话加一个真链接：「这次分析这一章。想读整本书？去全书分析 →」。

### 《我喜欢你的信息素》这本还剩什么（逐字段点过一遍）

显示的缺口补完了，内容上还剩两类，**其中只有一类是缺陷**：

| 模块 | 这本的实际情况 | 判断 |
|---|---|---|
| 拆文 | 9/9 满 | ✅ 已能看 |
| 故事 / 人物 / 悬念 / 节奏 / 章节 | 5 段结构、12 人、11 条悬念、76 个节奏点、76 条章节功能 | ✅ 齐 |
| 全书总览 | 19 个字段里 5 个有值 | **不是缺陷**：这两块是「评测」的产物，这本跑的是「拆文」。想要就在同一本书上再跑一次评测 |
| 综合诊断 | 9 个字段里 1 个有值 | 同上 |
| 人物档案 | 12 人里只有 2 人有完整档案：身份 0/12、结局 0/12、目标 2/12、重大选择 2/12 | **抽取覆盖不足**，非本书特有 |
| 主角历程曲线 | `axis: none`，0 个点（阶段卡和行动台账有） | **待修**，即清单里 D4 的曲线那条 |

人物那一条不是这本书的问题：拿另一本书的另一次运行（《系统豪横》run 18）对照，24 人里只有 1 人有弧光，
身份同样 0/24。查到源头——`_major_character()` 里 `identity` 和 `ending` **是写死的空字符串**，
其余字段只在模型为那个人返回了目标/选择事实时才填。引擎的注释说得明白：「推不出来的字段留空，不猜」。
这是诚实的设计，但产品结果是人物页列了 12 个人、其中 10 个点开是空卡片。

**同一处顺手修了一个真的缺陷**：没有 `to_lead` 事实时，这一行写的是字面量 `"unknown"`，
**被存进文档**并原样印到卡片上——第七轮 E7 在三个显示面上挡掉的那六条，源头就在这里。
改成写空字符串：空字段每个面都会丢掉，机器词不会。E7 那道过滤留着，它管的是已经存下来的旧文档。

### E9：分析完之后，想换成拆文没有入口——而且重新分析会偷偷换成评测

「评测 / 拆文」这个选择只画在**首次分析**面板上。一本书一旦有了结果，页面上就只剩
「重新分析 V2」，而那个确认面板里没有读法可选。

比没有入口更糟的是它并非「保持原样」：重新分析用的是组件里那个 `analysisMode` 状态，
默认值是 `diagnostic`。**一本按拆文分析过的书，点重新分析会被重跑成评测，而点的人从头到尾
没被问过一次。**

这和之前修短篇/长篇切换时那条理由是同一条：**一个在开头定死、之后无法更正的值，错了就是
永远错**。

改法：把那个 fieldset 抽出来，首次分析面板和重新分析面板共用；重新分析面板的默认值从
**这本书现有报告的读法**来（文档里有拆文内容就默认拆文），所以不改读法的人不会被换掉读法，
想换的人换得了。

顺带修掉一个连带的毛病：预估随读法变化，所以 prepare 查询的 key 带着读法——于是**换一次
读法整页会闪回「正在载入…」**，把报告丢掉再拿回来。加上 `placeholderData` 保留上一份，
换读法时页面不再空。

实测：《一梦如初》的报告是拆文，打开重新分析面板默认选中「拆文」；点「评测」能切过去，
面板和预估都在，页面不闪。

### E10：跑了第二种读法，第一份报告就没有入口了

E9 让人能换读法之后，立刻撞上下一个：一本书可以同时有评测和拆文，两者回答的不是同一个
问题，谁也不替代谁——但页面只认 `completed_v2_run`，也就是**最后跑完的那一次**。

于是「换读法」的代价是**把前一份藏起来**：钱花了、文档存在库里、没有任何入口能回到它。

后端补 `completed_v2_runs_by_reading`（每种读法各取最新的一次真实运行）。读法本身不在
runs 表里有列，流水线把它盖在 `engine_version` 上（`…-1.0+story_breakdown`），所以加了
`reading_of_run()` 把这件事收在一处，而不是让字符串手术散在 API 里。

前端在报告头上加一个开关，只在这本书**确实有两份**时出现——只有一个位置的开关不是开关。

## 十二、第八轮：把两条欠账做成通用能力（2026-08-21）

你要的是引擎的通用能力，不是针对这本书的一次性改动。两条都做了，实测结果一成一败——
败的那条把我原先的判断证伪了。

### ✅ 通用纵轴：从两种引擎扩到六种

`_JOURNEY_AXIS` 此前只有悬疑（认知度）和升级流（阶位），另外四种引擎落到 `axis: "none"`，
一条线都画不出来。现在每种引擎都指定一条轴：

| 引擎 | 纵轴 | 从什么清点出来 |
|---|---|---|
| 悬疑推理 | 认知度 | 悬念动作（原有） |
| 升级流 | 阶位 | 战力节拍（原有） |
| 情感关系 | 关系亲疏 | **新**：关系变化的 `change_kind`，八个封闭值带权重 |
| 权谋群像 | 戏份占比 | 出场分布（原有，此前只在 `pov=ensemble` 时生效） |
| 日常种田 / 无限流 | 得失累计 | **新**：每一程「获得」减「付出」的条数 |

**得失累计同时是兜底**——它只要每一程的得失条数，任何书都有。任何一条轴算不出点就回落到它；
两条都空才报 `none`，界面显示第七轮加的那句说明。

情感类此前画不出线的真正原因：`RelationshipChange` 只有一句自由文本（「从敌对到缓和」），
**加不起来**。补了 `chapter_ref` 和封闭的 `change_kind`，才第一次能放上时间轴。权重表与
`_COGNITION_WEIGHT` 同形：确立 +4、和解 +3、拉近 +2、初识 +1；疏远 −2、裂痕 −3、断绝 −4、
背叛 −5。

**实测**：《我喜欢你的信息素》主角历程 **0 点 → 44 点**，页签变成「关系历程」，跌得下去。

### ✅ 人物身份：0/18 → 22/22

`role_hint`（人物在书里的身份说法）L1 一直在抽，`max_length=40`，**全程被丢弃，下游没有一行
代码读过它**。现在折到人物行上，多个块里的说法取多数票——同一个人可能被写成「班长」和
「十班班长」，多数票选出更完整的那个。

`ending` 由该人物最后一次 `character_state_changes.to_state` 得出，按章排序。是清点结果，
不是对结局的判断。

### ❌ 目标/抉择覆盖：我的判断是错的，已撤回

我原先写的是「配额被主角吃光」。实测证伪：这次抽取给出 **20 条目标，只落在 2 个人身上**
（段嘉衍 13、路星辞 7），而配额是每块 4 条 × 10 块 = 40，**根本没用满**。

## 十三、第九轮：只留一个额度，并修好它的计数器（2026-08-21）

### E13：分析本章一直说「当前额度不足」，而钱一分没动

你点分析本章，弹窗写着「当前额度不足」，开始按钮是灰的。查下来：


**撞的是 Token 日限，不是钱**——我替你跑的四次全书分析把 80 万 token 用光了。而屏幕上
只有「当前额度不足」五个字：不说是哪条限额，不说明天零点会自动重置，「调整额度」按钮
在那里，你却不知道该调三个里的哪一个。

### 只留一条闸门：钱

三条日限量的是同一件事的三种单位——调用多就是 token 多，token 多就是钱多——却各自独立
地拦。每次分析那四个上限（调用次数 / 输入 Token / 输出 Token / 费用）同理，四个数字里
随便哪个填低了都能把人拦住。

| 原先 | 现在 |
|---|---|
| 每日请求上限、每日 Token 上限 | 只统计，不拦；设置里两个输入框已移除 |
| 每次分析：调用次数、输入 / 输出 Token 上限 | 只显示预估，不拦 |
| 每日费用上限、每次分析费用上限 | **唯一的闸门** |

用量照常逐项统计并显示——想知道用了多少看得见，能不能继续只问钱。文案也说清楚了：
「当前额度不足」→「今日费用已达上限，明天零点重置」。

### E14：而那个唯一的闸门，计数器是坏的

留下费用这一条之后，立刻发现它根本不准：

```
云端已发送调用 171 次，其中 estimated_cost 为 NULL 的有 121 次
```

`whole_book_v2/usage_ledger.py` 写入调用记录时带了 input/output/total_tokens，
**却从不写 `estimated_cost`、`currency`、`pricing_version`**。日费用统计对这些行求和，
于是跑了一整天全书分析，「今日已花」纹丝不动——**一个永远为 0 的计数器等于没有闸门**，
而它刚刚成了唯一的闸门。

按 token 与定价表算出价钱写进去，和单章分析走同一个 `estimate_cost()`。定价表里没有的
模型返回 None，仍然写 NULL：**宁可空着，也不要写一个编出来的价钱**——日闸门是按它拦人的。

实测 26.3 万输入 / 3.7 万输出的一次评测算出 ¥0.3384，与那次实际 ¥0.3924 同一量级。

### E17：三个环节互相等对方，而打破圈的那个动作没有入口

而它正卡在死锁的中间一环。

实测 connect → test：`eligible=True`、`blockers=[]`。

### E18：场景编辑功能没被删，是被一个从没打开过的开关关掉了

你说「把用户自己调整场景编辑的功能整没有了」。查下来更难堪——**功能一直在，只是出厂关着**：

```ts
export function getBoundaryReviewMode(): BoundaryReviewMode {
  // 只有 VITE_STORYLENS_BOUNDARY_REVIEW_MODE=manual_editor 才给编辑器
  return "confirm_only";   // ← 出厂默认，那个环境变量打包时从来没设过
```

同一件事有三个面板：

| 面板 | 能力 | 什么时候出现 |
|---|---|---|
| `ConfirmBoundaryDivisionPanel` | 只能接受 / 重新识别 | **分析流程里** |
| `SceneBoundaryReviewPanel` | 段落处拆分场景、相邻两场合并 | 工具栏「确认场景划分」 |
| `BoundaryReviewPanel` | 逐条候选接受/拒绝，带 conflict_code、first_pass_json | 开关打开时 |

于是划错了场景，除了「重新识别」（再花一次钱、结果还未必如意）之外没有别的办法。

改成分析流程直接落到能拆分/合并的那个屏幕。

## 十四、单章只做评测（2026-08-21，已定）

你问单章要不要也分拆文／评测。**定了：单章只做评测，拆文留在全书与短篇。**

理由不是偏好，是语料：`data/raw/breakdowns` 里 32 份长篇拆文拆的是整本（起承转合跨全书），
3 份短篇拆稿拆的是整篇（《活在真空里》19,911 字一整篇）——**一份按单章拆的都没有**。
拆文这件事天然是整篇尺度的，单章拆不出起承转合。记在这里，免得以后再翻出来重议。

### 拆文语料教给评测的一件事

真人拆文里**一个评分都没有**。他们写的是这种东西：

```
①【我永生难忘】和【不是高能案件】——产生疑问，什么样的普通案件能令人永生难忘呢
②【职业素养和为人道德的冲突】——主角会停止为学弟辩护吗？
```

原子形式是**【原文的具体词句】——它在读者心里制造了什么**。可核对、可模仿。

这条原则对评测同样成立：**数字不可核对，句子可以。**

### E21：类型专项的刻度只给了模型，没给读者

我先前说「`线索投放 0/5` 没有标尺」——**这话说错了两次，两次都要更正**：

1. 每条轴都带 `rationale`（「本场景未投放、推进或回收任何线索，仅过渡动作」），不是裸分；
2. 刻度也一直存在：`GenreAxis.anchors` 写明了 0/3/5 各是什么，而且文档解释了为什么必须有
   ——没有锚点时 `clarity` 在 42 个真实场景里 81% 都返回 5。

真正的缺口是：**锚点只进了提示词，没进响应**。读者看到一个分数和一句针对本场的理由，
却无从判断这把尺子严不严。同样地，`evidence_paragraph_ids`（这个判断看着哪几段做出的）
后端一直在产，界面一直没显示。

两样都在读取时挂上（按 key 现取，不写进存下来的产物），所以**这次改动之前跑的报告也能
看到**，而且刻度日后调整不会出现两份说法。屏幕上现在是：

```
线索投放                    0 / 5
本场景未投放、推进或回收任何线索，仅过渡动作。
▶ 这条怎么算分
依据：B0004-C0002-P0060、B0004-C0002-P0061
```

### E22：一个用来看的页面，成了写入方

你点全书分析，屏幕上是「无法读取数据 · 本地分析服务暂时不可用」。接口层面：

```
GET /books/4/whole-book/prepare  →  500
INSERT INTO whole_book_cost_estimates (book_id=4, 1299 章, 77749 段, 267 万字…)
sqlalchemy.exc.OperationalError: database is locked
```

**「准备全书分析」每被打开一次，就往库里插一行费用预估。** 而这个页面在有任务跑着时每
3 秒轮询一次——于是一个纯粹用来看的页面成了写入方，跟正在跑的分析抢同一把写锁。日志里
那 84 次 `database is locked` 全是它。《我不是戏神》1299 章的估算又慢，撞得更狠，最后连
它自己都 500。

**这一条我今早就查出来并报给了你，当时没修。** 它今天挡住了你。

改成先找现成的那一行：同一本书、同一版本、同一读法、同一模型，预估就是同一个数。有效性
判定复用既有的 `is_estimate_valid`——过期、书改了、换了 provider 或模型，都照样重算。

**这一条我第一次没修对，而且用一个错的证据宣布修好了。**

我改的是 `estimate_whole_book_analysis`，写的测试也只盯着它——测试绿了。但 prepare 根本
不调那个函数，它调的是 `estimate_hierarchical_whole_book_analysis_v1`。当时我的「验证」是
连打 5 次 prepare 全返回 200，然后数了一次行数说「13 行是历史的」——**我从没在调用前数过**，
所以那 13 根本不能证明任何事。

打包版跑起来后我数了前后：**13 → 18，五次调用涨了五行**，一行不少。修补完全没生效。

真正的修在 `whole_book_hierarchical_estimate_v1.py`：同一本书、同一版本、同一读法、同一
模型，就复用现成那一行。有效性就地判——版本哈希要一致（这一支存的是
`compute_book_revision_hash_v1`，和旧路径不是同一个函数，不能借用它的校验器），且未过期。
计划仍然现算，因为 `context_safe` 不在表里，凭空复用等于猜；现算是纯读，不占写锁。

实测（这次有前有后）：**调用前 18 行 → prepare 连打 5 次全 200 → 调用后 18 行。**

教训跟前面那三次是同一条，只是换了个形状：**测试绿了不等于产品好了——如果测试调的函数
不是产品调的那个。**

### 单章的结构化 PDF

你要的那份做完了：单章分析现在能导出一份 7 页的 A4 报告，跟全书那份共用同一道 Pro 门、
同一条打印路径（后端 `render_report_pdf`），字体嵌入和纸张一定一致。

它**只做评测**——这是我们上一轮定下来的：35 份人写的拆文汇总里没有一份是按章拆的，拆文
回答的是「这本书怎么搭起来的」，一章里没有那个问题的答案。封面上写了这句话，并指路到全书
分析去选拆文，免得读者以为是漏印。

顺序就是论证顺序：三项体检 → 曲线在哪掉 → 悬念欠了多少 → 逐场证据 → 能带走的写法 →
口径。类型专项那几条把 0/3/5 的刻度和依据段号跟分数印在一起，因为「线索投放 0/5」单独放着
只是一个数字。

《我不是戏神》第 1 章实测：HTTP 200，352 KB，7 页，中文不乱码。

**做的时候发现两个真错，都不是新写的：**

**账本三个数对不上。** 屏幕上写「本章开 5 收 3，走到章末仍欠 12」——5 减 3 不是 12。
`open_questions.opened/closed` 记的是**那一场**开了几个收了几个，只有 `balance` 是累计；
代码拿了末场的两个数当本章合计。全章实际是开 24 收 12，欠 12，这才对得上。屏幕和纸上都改了。

**附录解释了一份文件里没有的章节。** 没有类型专项的书，附录仍然在讲「类型专项那几条各有
自己的 0/3/5 刻度」，读者会去翻一张不存在的页。改成跟着那一节走。

另外画像轴里有「开篇抓力」「断章质量」，和第一页三项体检同名，但一个是 0—100 的钩子强度、
一个是 0—5 的画像档。同名时纸上直接说破，否则读者以为其中一个印错了。

### E24：三个多小时里，进程几乎一直在等网络

《我不是戏神》1299 章，全书分析预计 3.2 小时。你说正常应该 40 分钟左右，问是不是程序或
模型坏了。都没坏——**它一次只发一个请求**。

17 次调用的实测：16k 进 / 4k 出，`finish_reason=stop`，间隔稳定 58–77 秒，零重叠。每一次
都健康。4000 个输出 token 七十秒吐完，对 qwen3.7-plus 是正常速度。

163 个窗口是被**输出预算**卡出来的，不是输入：一次调用只写得出约 4k token 的事实，所以只
装得下 8 章，1299 ÷ 8 ≈ 163。输入才 16k，模型还有大把余量没用。

另外两条提速的路都不通：

- **块开大**：`MAX_CHAPTERS_FOR_SIGNAL_FIDELITY = 8` 是故意封的，代码里写明一块装 19 章时
  逐章计数会全变成 0。那是悄悄把分析变烂，比慢更糟。
- **换快模型**：能快，但抽取是要读懂剧情的活。

**所以只剩并发。** 块必须按顺序读——每块的提示词带着上一块留下的连续性状态——但那条链只
需要**在分区内**成立：分区本来就是归约单元，起承转合的边只落在分区边上，`reduce_partition`
也是按分区收的。改成每个分区自带一条链，分区之间并行，默认 4 路。

七十秒的模型调用是**唯一不持锁**的一步；共享状态（账本、证据、进度、SQLAlchemy Session）
全在锁内，那些操作是毫秒级的。store 和 provider 共用同一把锁，因为它们压着同一个 Session。

代价：分区头那一块看不到上一分区的连续性提示，163 块里有 27 道这样的接缝。选在分区边上是
因为那本来就是归约边界——接缝最便宜的位置，但不是零。

5 条测试盯着：并发不改结果、连续性链在分区内仍成立、**分区之间真的在时间上重叠**（不然
「并发」只是个名字）、并发=1 时逐块跑零重叠、计划没给分区时退回整本一条链。

**关于那 69 条失败：** 全量回归是 2615 通过 / 69 失败 / 18 错误，数字吓人，但在**没有这次
改动**的工作树上跑同样的文件，失败数一模一样（7 / 5 / 2）。是本来就坏的，不是并发改出来的。
这次没有像早些时候那样「看着像没问题」就宣布——先建了个 HEAD 的工作树做对照才敢说。

### E25：把「还没开始」画成了红色的失败

分析刚点下去，屏幕上是红色感叹号加「**无法读取数据**」。你说用户还以为失败了呢——对，

### E26：一本书起了两个任务，屏幕盯着死的那个

今天三个症状，同一个根：

    「卡死在 4%」           页面盯着空壳 run 15，真正在跑的是 run 14
    「点重新分析还是这界面」  孤儿任务把开始按钮堵住
    「余罪各种跳错误」       页面盯着空壳 run 20，跑完的是 run 19

《我不是戏神》相差 10 秒起了两个，《余罪》相差 14 秒起了两个。多出来的那个做完一两次调用
就杵住，而页面挑任务挑的是「最新的那个」。

**已有的幂等键拦不住**：它的输入含 `client_request_id`，每次点击都是新的——它防的是「同一
个请求重试」，不是「点了两次」。

三处一起修：

**心跳没人喂。** `last_heartbeat_at` 这一列早就建好，却只在取消时被写过一次；跑了 27 分钟
的 run 17 是 `None`。于是 `running` 既可能真在跑、也可能进程早没了，谁也分不出来。现在每写

**创建口不设防。** 这本书已有真在跑的任务时，创建接口把那个任务交回去，不再建第二个。

**页面自己挑任务。** 客户端按状态字段挑，可它凭状态永远分不出「在跑」和「死了但没人改状态」。
改成后端给 `live_run_id`，客户端照着渲染（INV-P4）。

判活用心跳而不是创建时刻，因为两个方向都是坑：用创建时刻，1299 章跑三小时的任务半路会被当
成僵尸；完全不判活，死掉的任务把开始按钮永久堵住——今天是我用取消接口手工解开的。

6 条测试盯这条边界，包括那两个反方向的坑。相关后端 427 条通过；那 4 条失败在改动前的基线
清单里逐条核对过，不是这次弄坏的。

### 「读懂」：专著与工具书的第三种读法（第一片）

你要的用途很具体：**读者没时间读，或者读不动英文，就想知道这本书到底讲了啥。**

小说那条线最贵的一步是「读完再猜结构」——起承转合是 163 个块烧出来的。专著不用猜：章首自带
带页码的小节目录，正文里每一节又以同样的编号起头。**结构是白给的，模型只需要填内容。**

这一片只做摄入层，因为那才是这条线真正的墙：

**PDF 接进导入口。** 逐页取文字并保留页边界——结构就藏在页眉重复和章首目录里，拼成一个字符
串就再也分不出来。扫描件单独报 `ScannedDocumentError`：它是好文件，只是还差一步 OCR；并进
「文件中没有可导入的文本」，用户会去换文件而不是去做 OCR。后缀是 .pdf 但内容不是的，翻译成
「这个文件不是有效的 PDF，或者已经损坏」，而不是把 `PdfStreamError` 甩给用户。

**结构识别 `detect_monograph`。** 实测那本 Handbook（四章 112 页）：**76 节，76 个精确定位，
覆盖率 100%，正文 77,712 词。**

过程里推翻了自己两次：

*空格不可信。* 同一个标题有三种面貌——`Usability T esting`、`5I N T E R A C T I O N`、
`Datavisualizationisabout`。为每种写一条规则，补一个漏一个（卡在 76/79）。最后删掉全部三条，
换成一条：匹配时把空白整个抹掉，另存位置映射表。三种面貌抹完都一样。

*页眉不能按样子认。* 第一版按某家排版厂的 `Trim Size: … Page NNN` 硬匹配，换本书就废。改成
让重复自己暴露：在多数页面同一位置重复出现的行就是版面家具。测试当场抓出这条的一个真缺陷
——四行的页面上「头三行+尾三行」覆盖整页，而数字被归一成 # 之后正文会被当成页眉删掉；边缘
宽度得跟页面长度走。

12 条测试盯这一层，盯的都是「会让内容静默消失」的边界——识别漏一节，读者不会知道自己漏了
什么。对知识类书来说，覆盖率是及格线，不是加分项。

**还没做：** 「读懂」这个读法本身（逐节摘要 + 上卷）、跨语言输出、类型分流（教科书要前置依赖
图，工具书根本不该被概括）。单节摘要已用真实调用验过一次：3276 词英文 → 一屏中文，九条主张
逐条回原文核对，无虚构，成本约 ¥0.02。

### 「读懂」第二片：格式与中文

你说原始文件可能中文可能英文，格式也要多支持一些——Word、PDF、还有论文常用的那些。

**支持的格式** ：TXT、DOCX、EPUB、PDF、Markdown、LaTeX、HTML/XHTML、ODT。全部用现成依赖，
没有为任何一种引新库。

**明确不支持的，要说清楚该怎么办**——含糊的「无法导入」会让用户反复换文件：

    知网 CAJ / NH / KDH   专有格式，请在知网页面改选「PDF 下载」
    MOBI / AZW3           请用 Calibre 转成 EPUB
    RTF                   请另存为 DOCX
    DjVu、扫描版 PDF       需要先 OCR 成有文字层的 PDF

**一个更重要的转向：能直接读到结构的，就别猜。**

原来的摄入把所有格式先拍平成一个大字符串，再拿小说的「第 N 章」正则去切。对小说 txt 没问题，
对专著是把现成的东西扔了——**Word 的标题样式、Markdown 的 `#`、LaTeX 的 `\section`、HTML 的
`<h2>`、ODT 的 outline-level，层级都是明写在文件里的**，读一下就有，比猜准得多也解释得清。
所以大纲带一个 `source` 字段：读来的（declared）可以直接信，猜的（inferred）必须让用户看见
规则和覆盖率。

**中文不是「顺带支持」，是另一套习惯。** `第三章` / `第二节` / `一、` / `（二）` / `§2` 都要
认，而且中文专著常常没有英文手册那种「章首自带带页码的小节目录」，只能从正文标题认。只会认
`3.1 Title` 等于只支持英文书。

**接线时抓到自己一个错。** 新写的逐行标题识别对 PDF 明显更差：264 节、71 个没有正文，还把
目录行本身当成了标题——因为我把上一片做好的 `detect_monograph` 晾在一边没接上。PDF 有页边
界（页眉重复、章首目录），那是它独有的信息，不用等于白扔。改回按页那条：**76 节、零遗漏、
75,983 词。**

13 条格式测试 + 12 条摄入测试 + 既有导入 6 条，共 31 条通过。

### 「读懂」第三片：真跑通了

7.6 万词的英文手册 → 中文报告，**76/76 节全覆盖，43 次调用，102 秒，约 ¥0.2。**

产出形状是按用途定的，不是「摘要」：**主张 / 依据 / 做法 / 术语 / 存疑**。主张必须是判断而不
是话题——「讨论了颜色原理」不算，「分类数据应当用色相区分、类别数不超过 12」才算。术语保留
原文词，因为读者要能拿它回到原文里去找。

**九条抽样核对，全部对得上原文，零虚构**：数据墨水量比、图形完整性、生态界面设计、工作域
分析、出声思维、形成性/总结性评估、远程测试、信息缩减。

三条设计要点：

**失败必须留痕。** 一次调用失败就静默跳过，等于让那几节的内容从报告里消失，而读者不会知道。
失败的单元照样进结果，带着原因，并把覆盖率拉下来；低于九成整份报告标为不可信。

**「拿回了字符串」不等于「成功」。** 模型答非所问却算进覆盖率，会让读者以为自己读全了。所以
没有主张的回答按失败计。

**并发不需要分区那套。** 节与节之间没有连续性依赖——这正是这条读法比小说简单的地方：小说的
块必须按顺序读（每块带着上一块的连续性状态），这里每节独立，直接并发。

**又一次栽在自己的核对探针上。** 九条里有一条报「原文找不到」，我差点写成模型虚构——真去翻，
原文写的是 `Maximize the data ink ratio`（无连字符），而我拿 `data-inkratio` 去找。今天第二
次了：**核对用的探针比被核对的东西还脆，等于没核对。**

顺手修一个真 bug：项目符号剥离把 `**该读**：…` 吃掉一个星号，报告里多出一个孤零零的星号。
项目符号后面必须跟空白才算项目符号。

25 条测试（规划 7 + 执行 10 + 摄入/格式沿用）。

### 「读懂」第四片：接进产品，成为第三种读法

界面上现在是三个并列的读法：

    评测   看自己的书：找出该改哪里、为什么、动的时候不能损伤什么
    拆文   看别人的书：起承转合、爆点在哪、钩子怎么下
    读懂   看不是小说的书：专著、教材、工具书

**挂在同一套任务机制上**——同一个 WholeBookRun、同一张进度、同一本记账、同一个心跳、同一套
重复任务防护。不是图省事：那套东西今天刚被打磨过（重复任务、心跳判活、写锁风暴），另起一套
等于把那些坑重新踩一遍。分流只在后台执行那一个点上分一支。

**但结果单独存、单独读。** 评测和拆文共用 `WholeBookAnalysisV2`，而这份产出是主张/依据/做法/
术语/存疑。硬塞进那个契约，就得给每个字段找一个不属于它的位置，读的人会以为它们是同一种东西。
所以用自己的检查点 stage 和自己的 `GET /whole-book-runs/{id}/comprehend`。

**报告的版面也刻意不同：可信度在最前面，不是末尾的小字。** 小说漏一段，报告读起来仍然完整；
知识类书漏一节，读者拿它替代原文，而他不会知道自己漏了什么。覆盖不足九成时，顶部直接写明
「有 N 节没读到，涉及那几节请回原文核对」；读失败的节留在原位并说出原因，而不是消失。

记账在锁内、模型调用在锁外——这个 ask 会被四个线程同时调用，而 Session 不是线程安全的。

前端 89 条通过，类型检查干净；后端相关回归 124 通过（1 条失败在改动前的基线清单里）。

### E27：能力加了，入口没开；验的环境不是产品跑的环境

你点导入，对话框里根本没有 PDF——写死的 `.txt,.docx,.epub`。**我加了能力却没打开入口**，跟
今早「单章 PDF 端点做好了但按钮拿不到任务号」是同一类漏：后端通了就以为完事了。

放开之后又撞到第二层：**打包版导入 PDF 直接 500**。

    ModuleNotFoundError: No module named 'pypdf'

我把 pypdf 写进了 PyInstaller 的 hiddenimports，但打包用的是 `.venv`，而它只装 pyproject 声明

段，76 个小节的层级全没了——而那正是这类书唯一有用的结构。改后 5 → 76。只对 PDF 开这条路，
别的格式保持原样，免得把一本 docx 小说切成一堆「1.1」。

**顺带一个误报。** 导入成功了却报「章节识别可疑」，原因是 `OVERSIZED_CHAPTER`——那条门槛
（一章超过五万字符）是给小说校准的：小说里这么长意味着切章失败。但专著的结构来自**书自己的
目录**，一节长就是长。照搬会让用户在一次完全正确的导入上反复去重新识别。结构来自原书目录时
跳过这套怀疑，小说路径一字未动。

打包版实测：**HTTP 201，76 节，1120 段，无警告。**

### E28：后端放行了，前端那道门还关着

你说「这里没有第三类分析的入口」。入口其实有——「读懂」就在全书分析页的三选一里。**但按钮
是灰的**，旁边写着「需要先确认作品画像」。

我上一条只修了后端的画像门，前端那道原样留着。**后端放行、前端不跟上，等于没放行**——我改
完后端就宣布「可以用了」，而你点开看到的是一个点不动的按钮。这比「没有入口」更糟：入口摆在
那儿，却不告诉你为什么用不了。

顺带把三处「这是给小说做的」措辞改掉。它们不挡功能，但每一处都在告诉用户「你手里这本书不属
于这儿」：

    我的书库 · 管理已导入的小说和分析项目   →  书
    [导入小说]                              →  导入书籍
    这是一部长篇，还是一个短篇？             →  这本书按哪种读法切？
    长篇 / 短篇                             →  整本 / 短篇，并写明专著教材走「整本」

**格式筛选那条是真会丢东西的**：勾选项只有 TXT / DOCX / EPUB，导进来的 PDF 会落进「其他」，
一筛就从列表里消失——用户会以为导入失败，而它好端端在库里。补齐八种，并且默认值改成从
`FORMAT_OPTIONS` 生成：手写一份漏了新格式时不会报错，只会让书悄悄消失。

3 条测试盯画像门的两个方向（评测/拆文照旧受约束，读懂放行，状态未知时不下结论）。前端 109 条
通过。

### E29：跑完的「读懂」页面看不见——于是你又付了两次钱

你说「进度显示还不稳定，一会儿又跳到了开始分析」。查库：**同一本书上有三个任务**（23、24 已
完成，25 还在跑）。你不是手抖，是页面每次跑完都跳回开始面板，你以为没跑成，就又点了一次。

原因：判断「这本书有没有完成的分析」那段，只认评测/拆文那种 `WholeBookAnalysisV2` 结果。
「读懂」的结果存在自己的检查点里——所以**一次成功的读懂，对页面而言等于不存在**。它跑完、
扣完钱、结果落库，然后页面表现得像什么都没发生过。

这条比「进度不稳」严重得多：**它让用户为同一件事反复付费，而且看不出自己在重复付费。**

三处一起认：完成判定认读懂的结果、读法归类认得出 `comprehend`、读法切换里它能出现。

顺带说明另一件事：重复任务防护没拦住这三次，是**对的**——23 跑完了才起 24，那不是并发重复，
是「用户以为要重来」。防护只挡同时在跑的，挡不住一个显示错误诱导出来的重复点击。**根在显示，
不在防护。**

2 条测试：跑完的读懂必须被页面看见；没有任何结果的「完成」仍然不算完成（放行它会显示一份
空报告）。相关 109 条通过。
